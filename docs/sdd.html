1. Introdução e Objetivo ▲ topo

Este documento descreve o desenho técnico do Sistema de Controle de Estoque, desenvolvido como parte da Fase 2 do Projeto Integrador Full Stack. Ele serve como referência única e viva da arquitetura, do modelo de dados e das decisões técnicas do projeto, sendo incrementado a cada etapa (não recriado do zero).

O sistema resolve um problema recorrente da gestão empresarial: controlar com precisão os produtos em estoque e seus fornecedores. A partir das histórias de usuário levantadas no desafio, o objetivo é entregar uma aplicação full-stack que permita a um gerente de compras/estoque cadastrar fornecedores, cadastrar produtos e gerenciar a relação muitos-para-muitos entre eles.

Público-alvo do documento

  • Desenvolvedores — como guia de implementação e de convenções.
  • Avaliadores do Projeto Integrador — como registro das decisões de projeto.
  • Manutenção futura — como ponto de partida para evolução do sistema.

Documentos relacionados

  • README.md — porta de entrada do repositório (como rodar, stack, status).
  • docs/00-visao-geral.md — documento mestre com o histórico de etapas.
  • Swagger UI (/docs) — documentação viva da API REST (a partir do backend).

2. Escopo Funcional ▲ topo

O escopo é composto por três features, cada uma com cenários de sucesso e de erro cujas mensagens ao usuário devem ser reproduzidas fielmente pela aplicação.

2.1 Fornecedor a implementar

Como gerente de compras, quero cadastrar fornecedores para gerenciar e rastrear as informações relevantes sobre os fornecedores com quem faço negócios.

Campos: nome da empresa, CNPJ, endereço, telefone, e-mail e contato principal (todos obrigatórios). O CNPJ é único no sistema.

Cenários

  • Sucesso: dados válidos e CNPJ inédito → cadastra e exibe "Fornecedor cadastrado com sucesso!"
  • CNPJ duplicado: já existe fornecedor com o mesmo CNPJ → bloqueia e exibe "Fornecedor com esse CNPJ já está cadastrado!"
  • Dados inválidos: campos obrigatórios em branco ou formato inválido → bloqueia e exibe mensagens de erro ao lado de cada campo.

2.2 Produto a implementar

Como gerente de estoque, quero cadastrar produtos para gerenciar e rastrear as informações relevantes sobre os produtos disponíveis no estoque.

Campos: nome (obrigatório), código de barras (único quando informado), descrição (obrigatória), quantidade em estoque, categoria (obrigatória — lista pré-definida Eletrônicos, Alimentos, Vestuário e opção Outro), data de validade (opcional) e imagem (opcional).

Cenários

  • Sucesso: dados válidos e código de barras inédito → cadastra e exibe "Produto cadastrado com sucesso!"
  • Código de barras duplicado: já existe produto com o mesmo código → bloqueia e exibe "Produto com este código de barras já está cadastrado!"
  • Dados inválidos: campos obrigatórios em branco ou formato inválido → bloqueia e exibe mensagens de erro ao lado de cada campo.

2.3 Associação Produto/Fornecedor a implementar

Como gerente de estoque, quero associar fornecedores aos produtos para rastrear de quais fornecedores adquiro cada produto e gerenciar melhor as relações de compra.

Relação muitos-para-muitos: um produto pode ter vários fornecedores e um fornecedor pode fornecer vários produtos.

Cenários

  • Associar com sucesso: seleciona um fornecedor e confirma → associa e exibe "Fornecedor associado com sucesso ao produto!"
  • Associação duplicada: fornecedor já associado ao produto → bloqueia e exibe "Fornecedor já está associado a este produto!"
  • Desassociar: remove um fornecedor associado → exibe "Fornecedor desassociado com sucesso!"
Status de implementação: nesta Etapa 0, todas as features estão apenas especificadas. Conforme cada módulo do backend for concluído, o respectivo item será marcado como implementado, com referência à tag correspondente na Swagger UI (fornecedores, produtos, associacao).

3. Arquitetura Geral ▲ topo

O sistema é um monorepo com dois aplicativos independentes — a API (backend) e a interface web (frontend) — que se comunicam por HTTP/REST. A persistência é feita em SQLite via Sequelize, e o contrato da API é publicado de forma viva pela Swagger UI.

3.1 Componentes

  • apps/api (NestJS): expõe a API REST. Organização feature-first (um módulo por domínio: fornecedores, produtos, produto-fornecedor), cada módulo com controller, service, module, DTOs e entity.
  • apps/web (Next.js): interface web (App Router) que consome a API via NEXT_PUBLIC_API_URL, seguindo o contrato publicado na Swagger.
  • SQLite + Sequelize: persistência local em arquivo; schema versionado por migrations e populado por seeders (sequelize-cli).
  • Swagger UI (/docs): documentação viva do contrato REST, gerada por @nestjs/swagger — fonte oficial dos endpoints da API.
  • packages/shared-types: reservado para tipos/DTOs compartilhados entre backend e frontend em etapas futuras.

3.2 Estrutura de pastas do monorepo Etapa 1–2

O esqueleto do monorepo foi criado na Etapa 1 e o backend foi scaffoldado na Etapa 2 (apps/api). O frontend (apps/web) e o pacote de tipos (packages/shared-types) seguem vazios (com .gitkeep) até serem preenchidos nas próximas etapas. 

estoque-app/
├── apps/
│   ├── api/                    # backend NestJS + Sequelize + SQLite + Swagger (Etapa 2)
│   │   ├── src/                #   main.ts, app.module.ts, config/, common/, <features>/
│   │   ├── database/           #   estoque.sqlite (gerado em runtime, ignorado)
│   │   └── package.json …
│   └── web/                    # (vazio) frontend Next.js — scaffold na Etapa 7
│       └── .gitkeep
├── packages/
│   └── shared-types/           # (vazio) tipos/DTOs compartilhados (futuro)
│       └── .gitkeep
├── docs/
│   ├── 00-visao-geral.md       # documento mestre (histórico de etapas)
│   └── sdd.html                # este documento
├── .gitignore
└── README.md

Internamente, apps/api/src segue a organização feature-first: um diretório por domínio (fornecedores/, produtos/, produto-fornecedor/), cada um com module, controller, service e as pastas dto/entities; mais config/ (conexão do Sequelize) e common/ (recursos transversais).

3.3 Documentação viva da API — Swagger UI Etapa 2

A API expõe sua documentação OpenAPI de forma viva, gerada a partir do próprio código por @nestjs/swagger:

  • Swagger UI: http://localhost:3000/docs — interface navegável, fonte oficial do contrato dos endpoints da API.
  • OpenAPI JSON: http://localhost:3000/docs-json.

O documento já declara as tags por domínio (fornecedores, produtos, associacao); os endpoints serão preenchidos sob cada tag conforme os módulos forem implementados (Etapas 4 a 6).

Versionamento: apenas a documentação viva (README.md, docs/00-visao-geral.md, docs/sdd.html) e a estrutura de pastas são commitadas. Os registros de etapa docs/NN-*.md ficam fora do Git (regra no .gitignore). O padrão de mensagens de commit é Conventional Commits (feat, fix, chore, docs).

A estrutura de pastas acima é a real (Etapa 1). Detalhes internos de cada app (configuração do Swagger, caminho do arquivo SQLite, organização feature-first dos módulos) serão adicionados a esta seção conforme os scaffolds forem concluídos.

4. Modelo de Domínio ▲ topo

Três entidades compõem o domínio: Fornecedor, Produto e a entidade de associação ProdutoFornecedor, que materializa a relação N:N.

Diagrama entidade-relacionamento (texto)

  Fornecedor 1 ────< ProdutoFornecedor >──── 1 Produto
                     (produto_id, fornecedor_id)
                     UNIQUE(produto_id, fornecedor_id)

  Um Produto  N ──── N  Fornecedor   (muitos-para-muitos)

4.1 Fornecedor (tabela: fornecedores)

AtributoTipo (Sequelize)ObrigatórioRegras / Observações

nome_empresaSTRINGsimNome da empresa
cnpjSTRINGsimUNIQUE · formato 00.000.000/0000-00
enderecoTEXTsimEndereço completo
telefoneSTRINGsimFormato (00) 0000-0000
emailSTRINGsimFormato de e-mail válido
contato_principalSTRINGsimNome do contato principal

4.2 Produto (tabela: produtos)

AtributoTipo (Sequelize)ObrigatórioRegras / Observações

nomeSTRINGsimNome do produto
codigo_barrasSTRINGnãoUNIQUE quando informado (múltiplos NULL permitidos no SQLite)

4.3 ProdutoFornecedor (tabela: produto_fornecedores)

AtributoTipo (Sequelize)ObrigatórioRegras / Observações
idINTEGERsimPK, auto-incremento
produto_idINTEGERsimFK → produtos.id
fornecedor_idINTEGERsimFK → fornecedores.id
created_at / updated_atDATEsimTimestamps automáticos

Restrição de unicidade: índice único composto em (produto_id, fornecedor_id) — impede associar o mesmo fornecedor ao mesmo produto mais de uma vez (base do cenário "Fornecedor já está associado a este produto!").

Os tipos acima refletem a intenção de projeto. O schema definitivo (tipos de coluna exatos e constraints) será consolidado nesta seção na etapa de migrations (sequelize-cli).

5. Decisões Técnicas ▲ topo

Por que NestJS?

Framework Node.js opinativo e modular, com injeção de dependências e arquitetura em módulos/controllers/services que favorece separação de responsabilidades e testabilidade. Integra-se nativamente a class-validator (validação de DTOs) e a @nestjs/swagger (documentação automática), atendendo diretamente aos requisitos de validação por campo e de API documentada. Foi a stack sugerida no material do desafio.

Por que Sequelize (+ sequelize-cli)?

ORM maduro para Node.js com bom suporte a SQLite e a relações muitos-para-muitos (belongsToMany), essenciais para a associação Produto/Fornecedor. O sequelize-cli traz migrations e seeders, permitindo versionar a evolução do schema e popular dados de exemplo de forma reproduzível.

Por que SQLite?

Banco relacional sem servidor, baseado em arquivo, com configuração mínima — ideal para o MVP e para o contexto acadêmico do projeto (o próprio desafio sugere o SQLite para teste da aplicação). Mantém a portabilidade e, por usar SQL padrão via Sequelize, permite migrar para PostgreSQL/MySQL no futuro com baixo atrito.

Por que Next.js?

Framework React de referência, com App Router, TypeScript, roteamento por arquivos e boa experiência de desenvolvimento. Suporta as telas do desafio (/fornecedores, /produtos, /produtos/[id]/fornecedores) e integra-se facilmente ao consumo de uma API REST. Foi a stack de frontend sugerida no material.

Decisões transversais

  • Monorepo (apps/api + apps/web): mantém backend e frontend no mesmo repositório, facilitando versionamento conjunto e futuro compartilhamento de tipos via packages/shared-types.
  • Swagger como contrato vivo: a documentação da API é gerada a partir do código, reduzindo divergência entre documentação e implementação.
  • Conventional Commits: histórico de commits padronizado e legível (feat, fix, docs, chore).
  • Documentação em camadas: README (como rodar) · visão geral (histórico) · SDD (desenho técnico) · Swagger (API) — cada artefato com um propósito claro.
